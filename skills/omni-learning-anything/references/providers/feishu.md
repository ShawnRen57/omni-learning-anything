# 飞书 / Feishu

Default new connection: official `lark-cli` user API transport, or an already authorized writable official API connector. The learner provides the course drive-folder link; the agent runs `connect --platform feishu --location LINK`. Document/Wiki links are not folder locations. This read-only check is separate from actual import permission.

The agent checks the official CLI's current help and `auth status --json --verify`. If no application is configured, initiate `lark-cli config init --new --brand feishu --lang zh`; inspect existing profiles first and preserve them (a new named app can use `--name NAME`). Forward the exact generated official setup URL with a PNG QR generated by `lark-cli auth qrcode URL --output FILE`. The user chooses their test/course organization and reviews app creation/permissions; browser login does not replace this setup. Wait for setup completion, then initiate the separate user grant with only the needed docs/drive scopes: inspect current endpoint schemas/help, prefer exact missing scopes, otherwise `auth login --domain docs --domain drive --no-wait --json`. Never request all domains as a shortcut.

Forward the exact `verification_url` plus generated QR and ask the learner to confirm completion. Keep device code in private session state; after confirmation the agent runs `auth login --device-code CODE` (with the same selected `--profile`), then rechecks verified user identity. On expiry generate a fresh flow with the same needed scopes; do not repeatedly reissue codes while organizational permissions are unchanged. Do not expose raw credential output. Admin/app scope availability and the user's grant must both allow the operations.

Successful `connect` returns `mode: cli`, pinned `account_id`, folder token and optional `cli_profile`; copy it into the new course. All API calls explicitly use `--as user`. Never substitute bot-owned documents or international Lark. Missing permission errors retain the existing task/document and request the smallest concrete correction. The adapter reuses raw official API commands for DOCX endpoints that have no typed command; this still writes through official APIs.

Existing `mode: api` supports private `credential_env.token`, or `credential_env.app_id` + `credential_env.app_secret`. App/tenant ownership differs from the learner's user identity; use it only when explicitly intended and verify learner access. The bundled endpoint is `open.feishu.cn`.

API flow: upload embedded-image DOCX to `/drive/v1/medias/upload_all` with `parent_type=ccm_import_open`; create `/drive/v1/import_tasks` with `type=docx`, `file_extension=docx`, and confirmed folder mount; persist ticket; query `/drive/v1/import_tasks/{ticket}`. Success is `job_status=0` plus a document token/URL. A processing result remains pending. Read `/docx/v1/documents/{id}/raw_content` and paginated `/blocks` to check sections, image block and all hyperlinks. No local image path is sent to the cloud.

Ask for the minimum documented scopes for media upload, document import/read and the selected folder; verify actual API permissions rather than inferring them from app publication. App credentials stay only in the named environment. Tokens are not persisted. Folder/doc tokens in the receipt are object identifiers, not account credentials.

UI fallback: import the embedded DOCX through the user's confirmed folder and choose conversion into a Feishu document, not a file attachment. Open the result, inspect all content and record the actual document URL/ID. Manual import is not an unattended automation claim. If upload stalls or fails, inspect the existing transfer task and destination before retrying; a file picker selection or upload queue entry is not a cloud document. Preserve the existing course and diagnose the actual failure before creating another upload.

Real-account history: the 2026-10-18 browser upload failed; a separate 2026-10-25 browser Word import passed for plan and Day01, including full content, figures, five exact URLs, title/folder placement, save/reopen and receipt reuse. Those are UI import results, not CLI/API acceptance. See the repository's dated reports for any later API results; do not relabel UI success.
