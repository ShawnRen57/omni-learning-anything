A ten-minute routine

Reserve seven minutes for the day's explanation and diagram, then three minutes for a short trace or choice question. You can answer aloud. No IDE, account, API key, paid service or project submission is needed. If a trace takes longer, stop after finding the first uncertain step and begin there next time. A useful learning record can be a single sentence describing what changed in your understanding.
Watching a full original lecture or doing an official problem set is optional work outside this ten-minute budget. The original course has a substantially larger workflow, including problem sets and a final project. [S1] A micro lesson is a starting point for that work, not a compressed claim of equivalent credit.

Days 1 and 2: Week 0

Day 1, “From a problem to an unambiguous procedure,” takes one subsection of u01. You will distinguish the item a procedure receives, the decision it makes, and the result it returns. Day 2, “Decisions and repetition in Scratch,” stays in u01 and connects the same reasoning to blocks. The goal is to predict a small behavior before running it, including what happens when there are no items.
Keep the examples tiny. Three parcels are enough to expose an unclear rule. Extra complexity can hide a misunderstanding behind mechanical work. Success means explaining why the procedure stops and giving one input on which a vague alternative fails.

Days 3–6: a route through two more groups

Days 3 and 4 belong to u02, C and arrays. “From blocks to C and arrays” introduces how a value and a position can be tracked; “Checking a small array calculation” uses a short trace to locate an indexing error. Days 5 and 6 belong to u03, algorithms and memory. “Comparing ways to search” asks how the arrangement of input affects the strategy. “Memory and the limits of a model” introduces the distinction between a value and its storage location.
These titles name our selected learning tasks, not replacements for official week titles. Reading about a loop once is not the same as being able to write and debug a program. At the end of six days, decide which group deserves another pass before moving forward.

How to check understanding

For each example, ask three things: What would count as the right answer? Which step makes progress? What could go wrong at the boundary? Try a normal case and an empty case before inventing a complicated one. If two readers execute your instructions differently, identify the ambiguous phrase and improve it. This is a more informative result than merely saying the instructions seem sensible.
The lesson diagram contains no benchmark data. Its arrows represent the order of an original toy procedure. Read those arrows as control flow, not as evidence that every computer program has exactly this structure. Later programs can keep running, accept new input, or make several outputs.
