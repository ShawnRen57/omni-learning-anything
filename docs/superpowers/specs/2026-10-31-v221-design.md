# v2.2.1: guided intent and verifiable readiness

The user approved the research roadmap and instructed implementation of v2.2.1, adding automatic interpretation of vague or concise learning requests. This design implements that authorized scope. Work happens on `codex/v2.2.1` in the existing checkout; prior research drafts remain separate.

## Learner experience

Use the host model to understand the request semantically, never a character-count/keyword classifier. Distinguish concise but actionable requests from broad topics, ambiguous meanings and ambitious/unrealistic goals. Reuse supplied preferences. For ambiguity that changes the course, offer a small set of concrete interpretations and ask the most useful question. Otherwise offer an editable recommended scope, prerequisites, observable outcomes and ordered modules, clearly labeling assumptions. Topic exploration must improve coherence and depth rather than adding irrelevant topics or silently expanding the user's goal. A proposed brief and plan do not approve a course or authorize schedules.

`references/intent.md` holds the decision process, subject-appropriate criteria and examples. An optional `learning_brief` in config preserves the original study request, interpretation, outcomes, included/excluded scope, prerequisites, sequence and explicit assumptions. It is protected by the existing config hash after approval. `brief-check` validates that contract, not semantic quality or user consent. Legacy configs remain valid.

## Readiness

Extend the current `doctor`, retaining its legacy fields and lazy PDF behavior. Check only selected formats' Python modules and TeX discovery, writable archive and local delivery configuration. Do not make network calls, read credentials or create remote documents. Configuration readiness, foreground host capability evidence and background evidence are distinct.

An optional host report is an explicit host attestation, not automatic proof. It carries host name, current course path and config hash, execution context, timezone-aware timestamp, and per-capability status/evidence. The caller supplies the expected host; background evidence additionally binds the actual job ID registered in the active approved non-sample course. Missing, stale, differently scoped or foreground-only evidence never certifies unattended operation. Required host capabilities are execution, research, images, inspection and notification, plus scheduler and cloud credentials in background mode. A real runtime observation must supply the evidence; the Skill must never fabricate it. Renderer success, connection readiness and remote write/readback remain separate.

## Onboarding observations

Add private course-local event recording before initialization as well as afterward. Fixed event/stage enums, idempotent event IDs, actual record times, positive user-action counts and optional explicitly metered usage prevent collecting free-form errors, URLs, account details or credentials. Summary exposes elapsed milestones, separately accumulated authorization waiting and only recorded interaction counts. Unknown cost stays unknown; partial usage is labeled partial. Events never touch approved config, plan, manifests, receipts or learning progress.

## Acceptance and delivery

Test missing dependencies without importing PDF, missing/stale/wrong-scope/background reports, idempotency, invalid metrics, restart persistence and legacy configs. Evaluate realistic brief scenarios, including vague subjects, concise specific goals, ambiguous terms and previously supplied information. Update ten README variants, version metadata, changelog, commands and setup/recovery guidance; build and validate a v2.2.1 ZIP without changing old archives. Use existing unit/integration tests plus isolated CLI workflows. Actual account/background checks are reported only if performed; no fabricated acceptance or activation statistics. Publishing to GitHub is a separate action from creating the local release candidate.
